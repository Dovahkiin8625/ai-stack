# 提示工程基础：让 LLM 听懂你要什么

写好 prompt 是用好大模型的"基本功"。很多人把大模型当作黑盒，同样的问题改几个词效果天差地别——背后是 prompt 在工程。本文系统讲解清晰指令、上下文结构、零样本与少样本之间的取舍，并给出一个生产可用的"翻译+摘要+JSON 输出"复合 prompt 示例。

## 一、为什么 prompt 决定了 LLM 表现的 80%

LLM 本质是一个**给定上文、预测下一个 token**的条件概率模型：

$$
P(y_t \mid y_{<t}, x) = \mathrm{LLM}(x \oplus y_{<t})
$$

其中 $x$ 是输入 prompt，$y$ 是输出。这意味着**模型的一切输出都由 prompt 决定**：模型没有"主动意图"，它只会"按上文最像答案的方式继续写"。所以：

- 同样的问题，写法不同等于让模型处于不同的条件分布。
- prompt 不只是"问问题"，更是**给模型限定解空间**。

经验法则：在很多业务任务上，**精心设计的 prompt 就能达到甚至超过微调小模型的效果**。先调 prompt 再考虑 fine-tuning，几乎是工业界的标准流程。

## 二、清晰指令的 6 条原则

写指令时，把任务"说人话、说具体、说边界"就够了。下面六条是工程上反复验证有效的：

1. **明确任务动词**：用"分类 / 抽取 / 改写 / 总结 / 翻译"等具体动词，不要用"处理一下"。
3. **给出输入/输出长度限制**："用三句话"、"不超过 80 字"、"返回 JSON"。
4. **给出边界与反例**："如果资料中找不到答案就回答'不知道'"、"不要编造引用"。
5. **指定输出格式**："先给结论再给理由"、"用 bullet 列出"。
6. **给出示例**（详见 few-shot 一文）。

> **反例**：`帮我看看这段文本` —— 模型不知道你要摘要、翻译还是抽取。
>
> **正例**：`把下面这段文本用三句话总结，要求保留所有数字与日期` —— 任务、对象、约束都明确。

## 三、上下文结构与角色设定

LLM 对 prompt 中**信息的顺序**很敏感。一个常用的稳定结构是：

```
[角色设定] -> [上下文/背景] -> [任务描述] -> [输出格式] -> [示例] -> [用户输入]
```

例如：

```text
你是一名资深技术编辑（角色）。
下面的内容是一段 API 文档（背景）。
请把它改写成给初中生看的科普短文（任务）。
要求：第一人称 / 不超过 200 字 / 包含一个类比（约束）。
输出格式：先给标题，再给正文（格式）。
示例：<原为示例>（示例）。

原文：{{input}}
```

角色设定（"你是资深 X"）不是"玄学"——它通过上下文激活了模型内部的某些先验分布，让风格更稳定。

## 四、零样本 vs 少样本

- **零样本（Zero-shot）**：直接给任务，无任何示例。优点是省 token，缺点是模型对"你想要什么格式"理解不稳。
- **少样本（Few-shot）**：在 prompt 中塞几个 `(输入, 输出)` 示例。LLM 会"模仿"示例的格式和风格。

经验法则：

| 场景 | 推荐 |
| --- | --- |
| 任务直观、输出格式固定 | Zero-shot 即可 |
| 输出格式复杂（JSON、自定义结构） | Few-shot（1-3 个示例） |
| 任务边界模糊 | Few-shot + 边界示例 |

## 五、复合 prompt 示例：翻译 + 摘要 + JSON

下面是一个完整的复合任务 prompt**，同时**做翻译、摘要、并要求 JSON 输出。这是生产中最常见的"既要又要"组合。

```python
import json
from openai import OpenAI

client = OpenAI()

PROMPT = """你是一名中英双语技术编辑。
请完成以下三件事，按 JSON 输出：

1. 把"原文"翻译成中文（保留所有专有名词、产品名、版本号不译）。
2. 用一句话总结原文的核心观点（不超过 30 字）。
3. 抽取 3 个关键技术术语（保留英文原文）。

输出格式必须是严格 JSON：
{{"translation": "<isite>", "summary": "<isite>", "terms": ["t1", "t2", "t3"]}}
如果原文不包含技术内容，terms 返回空数组。

# 示例
原文：RAG combines a retriever with a generator to ground LLM outputs in external documents.
输出：{{"translation": "RAG 将检索器与生成器结合，使 LLM 的输出以外部文档为依据。", "summary": "RAG 通过外部文档约束 LLM 输出，减少幻觉。", "terms": ["RAG", "retriever", "generator"]}}

原文：{input}
JSON 输出："""

def translate_article(text: str) -> dict:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": PROMPT.format(input=text)}],
        temperature=0,
        response_format={"type": "json_object"},
    )
    return json.loads(resp.choices[0].message.content)
```

这个示例演示了几个关键技巧：

- **任务清单 + JSON Schema**：让模型知道每件事都做，且严格按字段输出。
- **few-shot 示例**：示例同时示范了"原文非技术时怎么办"（terms 为空数组）。
- **`response_format={"type": "json_object"}`**：OpenAI 端直接保证 JSON 合法。
- **`temperature=0`**：解析类任务建议温度为 0，输出稳定。

## 六、常见基础坑

1. **指令含糊**："分析一下这句话"——分析情感还是抽取实体？效果方差极大。
2. **指令过长反而稀释重点**：把任务清单放在最前面，约束与示例放后面。
3. **未限制输出长度**：模型会啰嗦到把 token 烧光，同时把关键答案埋在中间。
4. **忘记指定否定行为**：必须说"不要做 X"时，模型才会主动避开。

## 小结

写好基础 prompt 的核心是：**清晰的任务动词 + 明确的边界 + 固定的输出结构**。把这三件事做好，零样本已经能解决大部分"格式规整"的工业任务。下一篇我们看 few-shot 与 in-context learning——如何在不微调的情况下用"示例"教会模型新技能。
